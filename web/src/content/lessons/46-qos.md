网络拥塞时，如果所有流量"公平"地一起丢，语音会卡、视频会花、关键业务会先崩。**QoS** 不增加带宽，它做的是在有限带宽里给不同业务不同待遇。

## 五个动作

```
分类（Classification）  按 ACL、端口、DSCP、应用识别业务
标记（Marking）         打 DSCP/CoS，后续设备直接信任
policing（监管）        超速直接丢弃或降级，守住承诺速率
shaping（整形）         超速先缓存，平滑发送，增加延迟
排队（Queuing）         PQ 优先、WFQ 公平、LLQ 低延迟队列
```

顺序很重要：**先分类、再标记，边界设备做监管/整形，拥塞点做排队**。如果每一跳不信任同一套标记，QoS 就会在边界失效。

## DSCP 与信任边界

DSCP 占 IP 头 6 位（0~63），常见取值：

```
EF = 46      语音，低延迟低抖动
AF41 = 34    视频
AF11 = 10    批量业务
CS6 / CS7    协议控制
BE = 0       尽力而为
```

终端可能乱打标记，所以接入交换机通常**重标记**或只信任指定端口；在信任边界之后，核心只需按 DSCP 排队。

## 监管、整形与队列

- **policing**：超速立即丢弃或降级，适合入口带宽约束；
- **shaping**：超速先缓存再平滑发送，适合出口向运营商承诺速率；
- **PQ/LLQ**：语音走优先队列，拥塞时先调度；
- **WFQ**：其余流量按权重公平分配；
- **WRED**：队列将满时按概率提前丢低优先级报文，避免所有 TCP 流同时降速。

## 在本模拟器里

模拟器实现了**广播风暴抑制**与**入方向限速**，能看到丢弃/抑制计数：

```
思科：
storm-control broadcast level 100
rate-limit input 1000
华为/华三：
broadcast-suppression 100
qos car inbound cir 1000
```

完整的 DSCP 队列、WRED、MQC 未建模，但"分类→标记→排队/丢弃"的框架与真实设备一致。

## 设计要点

1. 先确定业务等级（语音/视频/办公/批量/访客）；
2. 在接入层做分类与标记，核心层信任 DSCP；
3. 拥塞点配置 LLQ + WFQ + WRED；
4. 出口按运营商承诺速率做 shaping；
5. 用 `show qos` / `display qos` 的计数验证策略是否命中。

## 动手

打开实验九：给接入端口配置广播抑制，制造广播流量观察丢弃计数；再给上联口配置限速，观察超过承诺速率的流量被丢弃。然后思考：语音、视频、批量下载分别应该进哪种队列？
